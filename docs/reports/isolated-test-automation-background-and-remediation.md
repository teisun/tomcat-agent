# Tomcat 与 Multica 隔离自动验收：问题背景、根因与整改方案

> 按用户指定，本报告保留在源码仓库的 `docs/reports/`；一般调研归档仍遵循本目录 README 的 wiki 约定。
>
> **文档性质：背景与整改分析，附本轮实施与验收记录。** 第 1–7 节保留调查时的问题与方案语境，其中“拟改后”不单独构成完成证明；当前实现、真实验收结果及未覆盖边界以第 8 节和本轮证据为准。

## 1. 先看全貌

```text
你日常正在使用的 Tomcat
  ├─ 真实配置、会话、安装程序、正在工作的后台
  │    └─ 必须保护，不能让 AI 擅自修改或重启
  │
  └─ AI 修改代码后，需要验证代码是否真的可用
       └─ 另建测试专用环境
            ├─ 测试自己的 HOME、配置、工作目录
            ├─ 测试自己的 Tomcat 后台
            └─ 必要时启动独立 VS Code、浏览器和 Multica 接入测试
                 └─ 自动运行 → 检查证据 → 只清理自有资源

调查发现：这两类环境的边界处理不一致
  → 有些测试被错误拦截
  → 有些入口为了能跑，整体清除保护标记
  → 有些流程要求用户去终端接力
  → 个别失败清理路径仍可能过早删除测试资源
```

**核心结论：必要的是“不能误动用户正在使用的环境”，不是“真实测试必须由用户亲手输入命令”。**

本次应恢复的是已经审查、拥有私有资源的测试流程的自动执行，而不是拆掉正式环境保护。这里的“正式环境”不是专指线上服务器，也包括用户电脑上日常使用的配置、安装副本和后台服务。

## 2. 问题背景：为什么会有保护，又为什么需要自动测试

阅读提示：CLI 指命令行程序，CI 指代码仓库自动运行的检查；HOME 是程序据以寻找用户目录的环境变量。后文的 cwd 是当前工作目录，binary 是要运行的可执行文件，runner 是组织这些步骤的执行入口。

### 2.1 Tomcat 正在通过 AI 工具开发和测试自己

AI 可以通过 Tomcat 的 Bash 工具编译代码、运行测试，也可能在命令中再次启动一个 `tomcat` 程序。这叫嵌套调用。

如果新启动的程序仍使用用户的真实目录，就可能操作用户正在使用的状态。Tomcat 因此为 AI 工具启动的子进程设置 `TOMCAT_AGENT_ACTIVE=1`，并在 CLI 入口拒绝一部分嵌套变更操作。

这张标签可以理解为：

> “这条命令来自 AI 工具调用，不是用户在独立终端里的直接操作。”

当前源码明确将 `init`、`self-install` 等列为变更类命令；guard 在检测到标记值为 `1` 时拒绝相应操作。它按标记与命令分类判断，不会因为 HOME 是临时目录就自动放行。

依据：`tomcat/src/api/cli/mod.rs:486-558`，以及 CLI 执行前的调用点 `tomcat/src/api/cli/mod.rs:569`。

**保护标记是防误操作机制，不是操作系统沙箱。** 它既不能证明任意程序绝不会越界，也不能替代权限、路径和资源所有权检查。

### 2.2 自动测试不一定需要触碰用户的日常环境

| 用户日常环境 | 测试自己创建的环境 |
|---|---|
| 用户的配置目录 | 临时配置目录 |
| 正常会话与业务工作区 | 测试会话与临时工作区 |
| 正在处理任务的后台 | 测试专用后台 |
| 日常 VS Code profile 和扩展目录 | 独立测试 profile 和扩展目录 |
| 用户的模型账号 | 本地受控模型响应、假 key |

这就像：不能随便拆用户正在住的房子，但可以在专门的试验房里测试装修流程。

“夹具”（fixture）就是负责准备这些测试资源，并在结束后收尾的代码。项目已经具备相应夹具，例如 `tomcat-vscode-ext/scripts/realServeFixture.ts:14-32` 构造私有子环境，`tomcat-vscode-ext/scripts/realServeFixture.ts:61-81` 创建临时目录并用该环境执行初始化。

但**只换 HOME 不等于完整隔离**：环境变量还可能覆盖配置位置，VS Code 还需要独立 profile，服务和清理动作也必须指向测试自己的实例。隔离成立的依据是这些实际边界，而不是临时目录的名字。

### 2.3 为什么还涉及 Multica、VS Code 和浏览器

这些是不同层次的验收，不是一条单元测试可以替代的：

- **Tomcat 自身测试**：验证 CLI、会话、后台服务及其保护边界。
- **VS Code 扩展验收**：验证真实扩展安装包能否在独立窗口里正常工作。VSIX 是扩展安装包。
- **MCP 浏览器验收**：MCP 是模型连接工具的协议；这里验证工具发现、调用及真实浏览器行为，而不只是收到一句“完成”。
- **Multica 接入测试**：验证外部应用通过 ACP 调用 Tomcat 执行、取消、恢复任务。ACP 是两者之间的 Agent 通信协议。

这些测试可以使用真实 CLI、扩展、协议和浏览器，同时用本地受控 HTTP 响应替代付费模型。二者并不矛盾；但报告必须说明模型响应是受控的，不能宣称覆盖了真实模型服务。

| 执行口径分歧 | 原计划记录了隔离验收仍被要求切换独立终端、重复询问和搬运日志的情况 | 有些是 Agent 在执行前作出的判断，不是每次都实际启动后遭拒 |

## 4. 最明确的故障：Multica 的三行继承代码

### 4.1 原测试想验证什么

`TestTomcatSharedServeWithHermesClient` 是显式开启的跨仓真实协议测试。它要求指定本次构建的 Tomcat 二进制，用临时 HOME 和本地 HTTP 模型服务，不是要求登录真实模型账号的测试。

依据：Multica `../multica/server/pkg/agent/tomcat_integration_test.go:26-43`。

### 4.2 实际发生了什么

测试已经构造临时 HOME、工作目录和最小环境，但又执行了：

```go ../multica/server/pkg/agent/tomcat_integration_test.go:44-46
if active := os.Getenv("TOMCAT_AGENT_ACTIVE"); active != "" {
    env = append(env, "TOMCAT_AGENT_ACTIVE="+active)
}
```

当父环境的值为 `1` 时，因果链如下：

```text
外层 Tomcat Agent：active=1
        │
        ▼
Multica 创建临时 HOME 和工作目录
        │  但又把父 active=1 加回子环境
        ▼
测试 Tomcat 执行 init，准备自己的配置
        │
        ▼
CLI guard 看到 active=1，拒绝变更类命令
        │
        ▼
测试准备阶段失败
尚未进入真正要验证的执行、取消、恢复流程
```

因此，这个现象**不能直接证明 ACP 通信或执行逻辑坏了**。它首先证明的是测试启动环境与现有 CLI 保护发生冲突。

三行差异可以精确解释这一次启动拦截，无需为此重写 ACP、Multica 生产 backend 或共享服务架构。至于协议功能在当前版本上是否全部正常，仍需恢复启动后实际验证。

## 5. 全部问题不止三行：四个层面的边界不一致

| 层面 | 已发现的问题与依据 | 后果 |
|---|---|---|
| 执行规则 | 原计划列出的测试规范、扩展 README 和 runner 对隔离测试的处理不一致；VSIX MCP 入口仍按父标记拒绝，见 `tomcat-vscode-ext/scripts/run-vscode-verify-vsix.ts:322` | 一部分测试在尝试运行前就被转交用户 |
| 子环境构造 | Multica 给私有子环境加回父标记；Rust 总入口却整体清除标记，见 `tomcat/scripts/run-integration-tests.sh:28-31` | 保护范围忽大忽小，直接测试与经过总入口的前提不同 |
| 失败收尾 | Rust fixture 停服失败仅打印错误，见 `tomcat/tests/common/shared_serve.rs:46-72`；VSIX 外层 finally 仍删除安装根，见 `tomcat-vscode-ext/scripts/run-vscode-verify-vsix.ts:310-314` | 可能保留运行中的测试服务，却删除关闭或诊断所需的资源 |
| 回归发现 | 真实测试需显式开启，默认 CI 不保证实际运行；扩展现有快速门禁未收录相关 tests 目录中的环境契约 | 编译和部分绿灯不能发现“运行时启动被拒绝”，同类错误可能再次进入代码 |

Rust 的过宽清除发生在 gate 脚本进程及其下游，不是反向修改外层 Agent 的环境；问题在于清除发生在尚未逐一绑定私有资源的层次。它也不能作为“已经证明所有测试隔离”的证据。

TypeScript 还有一个易漏边界：`@vscode/test-electron` 会再次合并父环境。私有环境中被排除的键需要保留显式 `undefined`，否则仅删除属性可能让父值重新流入。方案因此不能只检查合并前的一份环境对象。

**把这些现象合起来看，根问题是：没有一致地规定谁负责构造测试边界、谁负责证明隔离、谁负责收尾。** 责任在总入口、具体测试和执行规则之间分散，最终一部分变成用户手工接力。

用户在独立终端执行同一脚本，通常只是改变调用环境；它不会自动修好配置隔离、服务所有权或失败清理。

## 6. 整改方案：保护不拆，责任归位

### 6.1 从第一性原理确定不变量

先确定必须同时成立的事实，再选择实现，而不是先寻找“如何让 guard 放行”的开关：

1. 用户正在使用的正式配置、安装副本和后台不被擅自操作。
2. 普通测试变更类命令在创建时就绑定测试自己的资源。
3. 测试不修改外层 runner 的保护标记和环境。
4. 模型凭据、配置覆盖只按测试场景显式注入。
5. 测试里的 AI 工具调用仍保留产品保护。
6. 未成功收尾不能伪装成成功，必要的控制和诊断资源不能过早删除。

由此推导出的结构是：

```text
外层 Agent / runner：保留保护标记
  │
  └─ 现有测试夹具：先准备并拥有私有资源
       │
       └─ 同一启动入口绑定 binary + HOME + 配置 + cwd + 子环境
            ├─ 测试 CLI：不继承宿主 Agent 标记和非场景所需配置
            ├─ CLI 内部真实工具 Bash：仍由产品设置 active=1
            └─ 收尾：结束自有连接/进程 → 停服成功 → 删除自有目录
                      停服失败 → 报告失败并保留 HOME、CLI 和日志
```

这里区分了两件事：经过审查的测试程序准备独立实例，与实例里的 AI 再次调用工具。只对子环境去掉宿主标记，不等于让测试里的 AI 从此没有保护；生产 CLI guard 不增加“临时目录自动放行”的分支。

### 6.2 具体改哪里

| 范围 | 拟议调整 | 刻意不做什么 |
|---|---|---|
| 规范与执行口径 | 明确已审查私有夹具可自动执行，Agent 直接跟踪任务与读取日志 | 不把正式安装、重启权限扩大为默认授权 |
| Rust 测试 | 复用现有隔离命令构造，迁移相关 CLI 测试后再删除 gate 整体清标记 | 不给任意命令增加无资源绑定的通用解除保护 helper |
| 扩展、VSIX、MCP | 复用 `realServeFixture` 的环境与生命周期，删除按父标记一律拒绝隔离验收的判断 | 不全局改 runner 环境，不用 fake 服务代签真实制品验收 |
| Multica | 恢复最小子环境，将测试专用环境和命令构造收敛为共用入口 | 不改变生产 backend/daemon 环境协议，不续做旧应用升级 |
| 失败清理 | 停服成功才释放目录；失败保留控制信息、程序和日志，并使测试失败 | 不全局 kill 同名进程，不创建后台清理服务 |

Rust、TypeScript 和 Go 复用各自已有工作流，不为了“统一”而新增跨语言框架或跨仓依赖。

### 6.3 为什么不只删三行就结束

如果只要求解除 Multica 这一次启动拦截，修正三行就是直接修复。但后续要求还包括防复发；此外，其他入口和失败清理已经有独立证据，不能用 Multica 的局部修复代替它们。

选择的最小闭环是：

> **同一启动源头 + 默认轻量契约检查 + 真实链路验收。**

不新增生产 test mode、授权令牌、环境注册中心、验收服务或新的状态协议。每个新增抽象都应能回答：删掉它，会失去哪项当前要求或必要安全保证？交付前还要做一次删除审查。

## 7. 如何证明修好，并防止同类回退

### 7.1 默认检查主动制造原故障的前提

普通 CI 往往没有 Agent 标记，不能依赖它自然重现问题。快速回归应主动模拟父环境：设置 `active=1`，加入模拟父 HOME、配置覆盖、会话模式和假 key 哨兵。

然后验证：

- 最终启动的测试子进程使用私有 HOME、配置和 cwd。
- 不该继承的宿主标记、配置和假凭据没有流入。
- 父环境和模拟父目录不变。
- 普通无标记启动仍正常；正式保护专项仍保持拒绝行为。

不拿真实用户 HOME 或正式后台做破坏性负例，也不打印真实凭据。

### 7.2 检查最终边界，不让单测验证另一套逻辑

- **Go**：默认回归与真实协议测试共用测试专用启动工厂；快速用例实际启动自身测试可执行文件，回报收到的环境和工作目录，不依赖已安装 Tomcat、账号或数据库。
- **Rust**：检查 gate 下游实际环境，再检查私有 CLI 真实初始化；仅检查脚本源码包含某个字符串不够。
- **TypeScript**：检查 fixture 环境经过实际 launch options 及父子合并后的结果，而不只检查最初的 env 对象。

Go 的辅助进程只证明启动契约，不能代替真实 ACP 验收。对应防回退要求已写入原计划 T10。

### 7.3 必须证明回归测试能抓住原缺陷

实施时保留原错误行为，先让同一回归失败；修正后再通过，记录“先红后绿”。Rust/TS 对应整体清标记和父值重新流入的已知反例，也应触发相应断言。

这是定向证明，不是新增变异测试平台；故意制造的失败须标明用途，不能算产品通过。

### 7.4 接入已有门禁，再做完整验收

轻量检查进入现有日常入口：Rust 默认目标、Multica 默认 agent 测试，以及扩展 CI 的定向环境契约步骤。不能只把断言加进需要显式开启的真实测试里。

完整验收再分别证明：

| 验证目标 | 应取得的证据 |
|---|---|
| 正式保护 | 模拟目录中的 guard 负例仍拒绝，内部工具 Bash 仍有标记 |
| 私有启动 | 从保留标记的 Agent 外层直接运行，CLI 正常初始化且只写自有目录 |
| 实例隔离与清理 | 两个自有实例互不干扰；清理失败非成功退出并保留必要资源 |
| VS Code 与 MCP | 当前 CLI 打包的真实 VSIX、实际 UI/浏览器行为、PNG、ARIA、console；由 Agent 读取证据 |
| Multica | 当前显式构建的 CLI、真实执行、取消后进程停止、同会话恢复及 registered backend 路径 |

快速回归用于尽早发现违约，真实链路用于证明集成可用，二者不能互相代签。模型响应使用本地受控服务，不宣称验证了付费模型服务。

不能承诺任意未来改动都绝不出错。可验承诺是：在已覆盖的启动与资源边界内，用默认门禁发现同类违约，并阻止将其当作合格交付；跳过门禁、未验证平台或远端 required checks 配置不在这一保证之内。

- 本轮未验证 Windows、Linux 或 arm64 原生环境，未修改远端 required checks。验收完成时尚未提交；本次提交阶段按用户要求不重跑测试，仅本地提交，不推送或发布。
- Rust / Go 的停服失败分支经过代码审查，未做故障注入；双实例正常停止不等于执行过失败分支。TS connectors 的实际无效 socket 失败确实保留了安装根，并以非零退出。
- 早期失败现场 `/var/folders/81/9fjf_p9n5f90_p5_mlsghtnr0000gp/T/tc-JWOSdE` 按失败保留约定留存，不因随后成功而删除；成功重跑的资源与最终进程核对见证据目录。私有工具与失败日志作为证据保留，不是后台服务。

## 总结

1. **背景：** Tomcat 要自动测试自己，但不能误动用户正在使用的配置、安装和后台。
2. **原因：** 正式环境与测试环境的边界处理不一致；Multica 三行继承是一个明确实例，不是全部问题。
3. **方案：** 保留正式保护，让现有夹具负责私有启动与清理，用默认回归发现同类违约，再以真实链路证明集成可用。
