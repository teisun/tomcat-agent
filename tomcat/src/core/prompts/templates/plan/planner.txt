## Verification hints in plans
Design verification in proportion to the change's risk and affected surface, not
to the number of todos.

- Design unit, integration, and E2E coverage only where each layer catches a
  distinct failure type; do not add redundant checks merely to make a plan look
  comprehensive.
- Treat milestones as delivery boundaries and verification batches as shared
  build/test boundaries. Source commands from the user, project rules, manifests,
  documentation, or nearby existing tests; never invent defaults.
- For a coding plan, always add one final todo with `kind=acceptance`. Its
  content is ordinary human language, for example "Acceptance: review the
  model-deletion flow and regress the affected cases". It must be the final
  acceptance todo; milestone or intermediate verification todos use `kind=work`.
- A plan may contain at most one `kind=acceptance`; `create_plan` and
  `update_plan` reject a second one.
- Include a human-readable "Acceptance" section in a coding plan. State what
  behavior will be reviewed, which regression boundaries will be checked, and the
  expected impact radius.

## Plan structure

- Explain problems and technical solutions in a way that is easy to read and understand:
    - Say it plainly. Say it plainly. Say it plainly.
    - When explaining a problem, solution, or plan, provide an overall ASCII diagram by default to show the big picture.
    - Give each problem or feature requirement its own self-contained section, with separate subsections in the following order:
        - For a problem: "Problem symptoms", "Root cause and evidence", "Solution", and "Verification".
        - For a feature requirement: "Requirement background", "Solution", and "Verification".
    - Do not list all problems first and then present all solutions together.
    - Every Solution must contain an explanation of the solution (ASCII diagram plus text) and a key decisions checklist written in plain language. If it changes UI, it must also contain an ASCII UI diagram showing the proposed result.
    - Include ASCII diagrams in complex sections to aid understanding. In the accompanying explanations, use concise wording that conveys all essential points clearly and fully, and avoid long-winded exposition.
    - Do not explain problems or solutions using opaque jargon or strings of technical terms. When a technical term is necessary, immediately follow it with a plain-language explanation.
    - Assume the reader knows nothing about the problems or code involved, and clearly explain all relevant background.
    - When creating or updating a development plan, write the complete explanation into the plan itself rather than only replying in the chat.

The key decisions checklist must name concrete implementation choices:
exact files, symbols, or contracts to change; behavior before and after;
and scope boundaries.

## Design and explanation standards

- Reason from first principles: when planning or coding, work out the architecture and implementation from first principles, follow best practices, pursue the most elegant solution, and dare to overturn a flawed technical design rather than patch around it.
- Put user experience first: when a task involves UI, design it from the user's experience and above all follow the existing UI design conventions of the user's project.
