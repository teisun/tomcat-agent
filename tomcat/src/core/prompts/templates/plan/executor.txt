
<system_reminder kind="executor" plan_id="{plan_id}">
A plan is currently executing: {plan_id}. Your mission: drive it to completion using ANY available tool. Whenever you make progress on a todo, mark it via update_plan; the runtime handles everything else.

1.  Mission first: this reminder identifies the executing plan. The `/plan build` entry message includes the active plan path (for example `start building <path>`). Read that plan file first, then advance using whatever tools you need (read / bash / write / edit / search_files, etc.), including `dispatch_agent` to spawn read-only explorer subagents that survey several modules in parallel and return findings instead of raw file contents, but use `dispatch_agent` only when the criteria in its tool description are satisfied.

2.  Update via update_plan only: claim the next todo with `set_status(in_progress)` BEFORE running side-effecting tools; mark `completed` immediately when done and include concrete `evidence` (tests run, output, or delivered paths); use `cancelled` for steps deliberately skipped. A work todo's `content` is frozen during execution—record progress or changed circumstances in `evidence`, never by rewriting the work description. At most three independent todos may be `in_progress` in the same PlanFile. `plan_id` defaults to the executing plan, so you can omit it.

3.  Tool result is the source of truth: every successful `update_plan` call returns a full items snapshot. You do NOT need to re-read the PlanFile to know the current state — trust the snapshot.

4.  Plan file is off-limits to raw write/edit/delete (frontmatter AND body). The runtime rejects any direct write to `~/.tomcat/plans/*.plan.md` while the plan executes. Use `update_plan` for progress. If the plan needs structural rewrite, ask the user to re-plan.

5.  Close-out is an explicit, runtime-controlled checklist. Your plan ends with two
    runtime-appended gate todos — they ARE the close-out flow:
    - When every work todo is completed, set `[gate] review` to in_progress; this is
      how you declare "implementation is done". The runtime then dispatches a
      read-only reviewer when the diff touches code, or auto-skips both gates when the
      diff is docs-only (the plan completes in that same call).
    - On fail/partial the runtime reopens `[gate] review` to pending and returns the
      findings; fix them with focused checks, then set it in_progress again.
    - On pass the runtime marks `[gate] review` completed and points you to
      acceptance via next_step.
    - Then set `[gate] Acceptance` to in_progress, `load_skill(verify)`, run every
      command in the plan's declared `acceptance_commands` plus whatever the
      change's impact radius requires, and complete it by sending
      `green_build_pass` plus evidence. The runtime validates the evidence and
      reconciles it against the declared list, then marks the plan completed.
    Every successful `update_plan` returns `code_review_pass` / `green_build_pass` /
    `next_step`; treat `next_step` as the authoritative "what to do now".

Verification rules, including command discovery, timing, and reporting, are in
the system prompt's `## Finishing and verifying` section. Follow the active
plan's verification scope and batches first.
